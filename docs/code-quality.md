# Xiranite 代码规范

这份规范服务于两类读者：维护代码的人，以及下一次需要定位和修改代码的 AI。目标不是让每个文件都短得不自然，而是让职责、边界、契约和验证路径可被快速恢复。

## 文件大小

维护源码的硬上限是 1000 个物理行，800 行开始预警。物理行包含空行和注释，使用统一的可执行检查器统计，避免不同编辑器产生不同结果。

纳入检查的目录是 `src/`、`packages/`、`scripts/`、`cmd/`、`native/` 和 `examples/`。纳入检查的源码扩展名包括 TypeScript、JavaScript、Rust、Go、CSS、Svelte 和 Vue。`vendor/`、`node_modules/`、`dist/`、`build/`、`artifacts/`、`migration/`、覆盖率和测试附件不属于维护源码门禁。

```text
bun run check:source-size   # 只检查当前修改；新文件超限或已有超限文件继续增长会失败
bun run audit:source-size   # 报告全仓库超过 1000 行的历史文件，不因历史债务失败
bun scripts/check-source-size.ts --all --strict  # 将全仓库超限视为失败
```

拆分 TS/TSX 前可先用仓库已有的 OXC AST 工具列出顶层声明和依赖，再进行同目录提取：

```text
bun run tsx:split --file src/path/Feature.tsx
bun run tsx:split --file src/path/Feature.tsx --target src/path/FeatureView.tsx --symbols FeatureView,FeatureViewProps
bun run tsx:split --file src/path/Feature.tsx --target src/path/FeatureView.tsx --symbols FeatureView,FeatureViewProps --write
```

提取默认只生成报告；`--write` 会拒绝部分变量声明、残留的同模块依赖和嵌套绑定遮蔽，并在写入前重新解析源模块与目标模块。工具只负责可证明安全的顶层声明迁移，组件内部的 hook、闭包和副作用边界仍需人工拆分和行为测试。

历史超长文件按债务处理：不要为了满足数字进行无意义拆分；但当一个任务已经触及该文件时，应优先按领域边界拆出模块，并至少保持文件不继续增长。常见拆分方向如下：

- React：视图、事件协调、状态 hook、纯展示子组件、类型和测试。
- 后端：路由、输入校验、用例服务、持久化 adapter、序列化和错误映射。
- Node/CLI：命令解析、领域 core、交互 schema、输出渲染和平台 adapter。
- 原生代码：公共契约、平台实现、生命周期管理和测试夹具。

## AI 可读性

### 修改前

AI 接手任务时必须先建立局部地图：

1. 找到入口、消费者、公共类型或协议，以及对应测试。
2. 确认数据流向和副作用边界，特别是 UI、HTTP、持久化、平台 adapter 之间的边界。
3. 搜索同类功能和成熟依赖，确认不会重复实现已有基础设施。
4. 明确本次修改允许触碰的文件范围；不因为顺手清理而扩大范围。

### 编写时

- 一个模块只拥有一个主要职责；入口文件以组装为主，不承载全部业务逻辑。
- 前端采用“纯 TS 核心、框架薄适配”：领域规则、数据转换、校验、状态机、选择器、缓存策略和请求编排优先放在不导入 React/Svelte/Vue 的模块里；框架组件只负责视图、生命周期、事件绑定和组合。
- 通过窄接口、显式输入输出和 adapter 隔离框架。共享的 domain、contract 和平台无关服务不能反向 import 具体框架；具体组件可以使用框架的强项来保持美观、模块化和开发效率。
- 用领域名词命名变量、函数、类型和文件。`config`、`data`、`value`、`handle` 这类泛名只有在局部上下文确实足够明确时才使用。
- 优先显式的数据结构和窄接口。输入、输出、错误和副作用要能从函数签名或邻近类型看出来。
- 把状态转换写成可搜索的命名函数；避免多处直接修改同一个对象、依赖隐式顺序或使用难以追踪的全局变量。
- 不使用为了省行而牺牲可读性的压缩表达式、深层三元表达式、无名大对象和跨多个边界的万能 helper。
- 注释解释“为什么这样做”、兼容旧行为的原因、平台限制或生命周期约束，不重复描述语句本身。
- 类型、协议和常量应放在稳定且容易被搜索到的位置；不要把关键契约藏在组件内部或动态字符串拼接里。
- 不要为了“可替换”新增一层没有实际边界价值的包装。框架抽象必须证明不会增加渲染、订阅、内存分配、包体或调试成本；性能热路径优先保留直接实现，必要时用基准或浏览器测试验证。
- 新增前端依赖前先检查当前依赖和成熟维护中的替代方案，记录 API、许可证、包体、运行时性能、维护状态和未来替换成本。纯 TS 能清楚承担的通用逻辑不应绑定框架或再引入库。

### 完成时

AI 交付前必须留下可复核的信息：

- 改了哪些文件，以及每个文件的职责变化。
- 保持了哪些既有契约，新增了哪些输入/输出/状态。
- 实际运行了哪些检查和测试；没有运行的门禁要明确说出。
- 是否存在历史超长文件、平台限制、未覆盖分支或需要后续拆分的债务。

## 验证和提交

验证命令按风险选择，不要用“能编译”代替行为验证：

- 纯逻辑：普通 Vitest。
- React 组件、交互、布局和视觉：Vitest Browser Mode，测试文件命名为 `*.browser.test.tsx`。
- Wails、原生窗口和跨进程行为：Go 或宿主集成测试。
- 代码结构：`bun run check:source-size` 和相关 lint/typecheck。

提交时只包含本任务拥有的文件，优先使用仓库的 `bun run commit "<message>" <path>...`。不要暂存或清理其他任务的修改。
