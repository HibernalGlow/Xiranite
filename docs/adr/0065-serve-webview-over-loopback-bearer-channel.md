# Serve the WebView over a loopback bearer channel instead of a gateway

## Context

Today the desktop path is `Wails WebView -> Go gateway (/ _xiranite/backend proxy) -> Bun backend`. The
gateway exists mainly to make the backend look same-origin to the WebView. That whole Go layer is
scheduled for deletion by ADR-0063, and the cross-origin shape changes with it: a Tauri 2 WebView is
served from the custom `tauri://`/`http://localhost` origin while Axum listens on a plain TCP socket.
Copying the current gateway mechanically is not an option, and this is the place where the rewrite can
be finished and then discovered not to connect.

The existing random-token security thinking is sound and is kept: the backend already requires a token
generated per instance, and `docs/随机端口.md` records the user's explicit dislike of random ports as a
hand-maintained address book.

## Decision

The Rust side binds Axum to `127.0.0.1` on an OS-assigned port. On startup the Tauri core process mints
`baseUrl`, `token` and `instanceId`, and the frontend obtains them through one Tauri command, then
talks HTTP:

```
React API client -> Tauri adapter -> HTTP -> 127.0.0.1:<port>  (Authorization: Bearer <token>)
```

Constraints:

- Loopback only. `0.0.0.0` and unauthenticated local listeners are not allowed.
- The token is per instance, generated by the Rust side, and required on every business route; a
  missing or wrong token is a 401, exactly as the current backend behaves.
- Browser development keeps the plain path: Vite dev server -> `fetch` -> local backend, with no Tauri
  adapter in the chain. The transport difference lives behind `src/backend/runtime/{web.ts,tauri.ts}`
  (ADR-0063 principle 1), not in call sites.
- Requests that need the Tauri HTTP plugin are scoped by URL to the loopback origin only.
- `tauri-plugin-localhost` is not used. It exists to serve Tauri's own bundled assets over a local
  server and its documentation warns of substantial security risk; Xiranite's assets are served by Vite
  or Tauri's asset protocol already, so the plugin would add exposure without removing any work.
- No compatibility proxy: the old Go gateway is deleted with the Go layer rather than kept running
  beside the Rust listener, and no dual-stack fallback is introduced if the channel fails. A failure is
  surfaced to the runtime status surface instead of silently re-routing.

## Alternatives considered

### All business calls become Tauri commands

Rejected in ADR-0063: it discards a working protocol layer, breaks the web target, and forces UI
rewrites for what is only a transport change.

### `tauri-plugin-localhost`

Rejected above (security posture, and it solves a problem this product does not have).

### Fixed port

Rejected. A fixed port collides with itself whenever a second instance or a stale process holds it,
which is the failure mode the current random-token design already avoids. Single-instance handling is
covered by the Tauri single-instance plugin plus deep-link instead.

## Consequences

Startup ordering becomes explicit: the frontend must not issue business requests until the channel
handshake resolves, which the existing TanStack Query backend-lifecycle gate already models (health
ready before snapshot load). The runtime settings surface reports `baseUrl`, API status and plugin
runtime status in place of the current Bun/backend-restart section (ADR-0063 principle 4). Verification
requires a real Tauri build on Windows, so the channel is one of the documented non-Windows gaps: it
cannot be closed on a macOS arm64 host without a Tauri smoke run.
