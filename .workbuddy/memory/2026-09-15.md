## 修复：所有节点命令行报 `ReactReconciler is not a function`

**症状**：任意节点的 CLI/TUI 启动即抛
`TypeError: ReactReconciler is not a function. (In 'ReactReconciler(hostConfig)', 'ReactReconciler' is an instance of Module)`。

**根因**：`node_modules/react-reconciler/cjs/react-reconciler.development.js` 被安装成 **0 字节**。
该包 `index.js` 在 `NODE_ENV !== 'production'` 时 `require('./cjs/react-reconciler.development.js')`，
空文件使 `module.exports = {}`，于是 `@opentui/react` 的
`chunk-hjtp6jv9.js`（`import ReactReconciler from 'react-reconciler'` → `ReactReconciler(hostConfig)`）拿到空对象。
上游同版本该文件应为 **750272 字节**，属本地安装截断/写入失败，非上游缺陷。

**为什么"所有节点"一起挂**：全部节点 TUI 走同一条共享链
`packages/nodes/*/src/Tui.tsx` → `@xiranite/cli-runtime/terminal/opentui` → `@opentui/react` → `react-reconciler`，
单点损坏即全节点崩，与单节点代码无关。

**修复**：从 registry 拉 `react-reconciler@0.33.0` tarball，校验 sha512 与 `bun.lock` 一致
（`KetWRytFv1epdpJc3J4G75I4WrplZE5jOL7Yq0p34+OVOKF4Se7WrdIdVC45XsSSmUTlht2FM/fM1FZb1mfQeA==`），
解包取 `package/cjs/react-reconciler.development.js`，写 `.tmp` + `os.replace` 原子替换回 `node_modules`。
修复后 sha256 与 tarball 成员一致，丢弃破损的 `node_modules` 缓存即可。

**验证**：
- `bun -e "require('react-reconciler')"` → `typeof = function`（修复前 `object`）
- `bun test packages/nodes/sleept/src/Tui.bun.test.tsx` → 1 pass
- `bun test packages/nodes/logx/src/Tui.bun.test.tsx` → 1 pass
- `bun packages/nodes/sleept/dist/cli.js --help` → 正常输出

**顺带发现（未处理）**：`node_modules` 内共 94 个 0 字节 `*.js/.mjs`。多数是上游本就空的
类型 stub / barrel（hono、elysia、lucide-react 等），但 `pdfjs-dist/legacy/build/pdf.mjs`、
`playwright-core/lib/serverRegistry.js`、`react-icons/fa/index.mjs` 等仍可疑，本次未逐一核实，
若后续出现"某依赖导出为 undefined"类报错，优先怀疑同一批截断。

**教训**：Windows 上 `bun install` 出现单文件 0 字节时，不要先怀疑版本/兼容性，先 `ls -la` 看体积；

## 调研：macOS / Linux 适配方案（产出 ADR-0063 提案）

用户问"添加 mac 和 linux 适配用啥 adapter 方案"。通读现有边界后结论：
**不新增跨平台 adapter 框架**，核心问题是 `*_other.go` 是"说谎的适配器"。

### 已就绪、不用动的部分

- **TS 宿主适配器**（`src/backend/adapters/{wails,web,denoDesktop}.ts`）抽象的是
  **宿主**（`RuntimeInterface.kind`），不是 OS；`detectWails()` 读 `window._wails`。
  已有 `WindowCapabilities.componentWindows: "native" | "browser-fallback" | ...`、
  `TrayCapabilities` 能力协商。保持不动，只需补 OS 维度上报。
- **原生产物机制**已经平台键控：`native/prebuilt/<platform>-<arch>/`、manifest 有
  `platform`/`arch` 字段、`build-native-assets.ts --refresh --no-build` 按
  `id:platform:arch` 合并资产、`native-loader/index.ts` 按 `process.platform`/`arch` 查表、
  `arcthumb-node/Cargo.toml` 用 `[target.'cfg(windows)']` vs `cfg(not(windows))` 分叉
  （`wic`/`windows-shell` 是 optional feature）、`czkawka_core` 上游跨平台。
- `native-loader/src/index.ts:94` 缓存根 `LOCALAPPDATA ?? XDG_CACHE_HOME ?? ~/.cache` 对 Linux 已正确。

### 真正的问题

1. **`*_other.go` 返回假成功**（8 对）——`node_app_instance_other.go` 的
   `acquireNodeAppInstance` 返回 `(inst, true, nil)` 即"宣称拿到单实例锁"但没加锁；
   `local_backend_containment_other.go` 全 no-op（丢掉 Job Object 的 `KILL_ON_JOB_CLOSE`
   等价物）；`external_node_launch_protocol_other.go` `return nil`。所以**"非 Windows 能编译"
   完全不能作为移植完成的证据**。唯一语义正确的是 `subprocess_attr_other.go`（`HideWindow` 无对应物）。
2. **TS/Rust 侧 4 处硬编码**：`packages/findz-native/src/index.ts:57` 与
   `build-native-assets.ts:21` 写死 `"findz.dll"`；`build-native-assets.ts:20`
   `platform === "win32" ? ["dav1d.dll"] : []`（czkawka 依赖 libavif，非 Windows 不打包 dav1d →
   运行时 dlopen 失败）；`build-native-assets.ts:49` 与 `native-loader/src/index.ts:85`
   库搜索路径仅 Windows 处理（Linux 要 `LD_LIBRARY_PATH`、macOS 要 `DYLD_LIBRARY_PATH`/`@rpath`，
   分隔符 `:` 而非 `;`）。
3. `service.go` 两处内联 `runtime.GOOS`：`:698` 的
   `window.OnWindowEvent(events.Windows.WindowEndResize, ...)`（决定组件窗口几何回写，
   非 Windows 上会静默失效）、`:864` 的 `primeWindowFrame`（Windows frameless 的 bounds 补偿，提前返回可接受但应声明）。
4. `native/Cargo.toml` 的 workspace members 只有 `arcthumb-core`/`arcthumb-node`/`czkawka-core`/`czkawka-node`；
   **`slimg-core` 与 `findz-go` 在磁盘上但未接入 workspace**。`findz` 是 Go 核心（见 ADR-0053）。
5. `native/vendor/dav1d-windows-x64.zip` 只有 Windows 来源；`arcthumb-core` 的 `unrar` 需 C++ 工具链，是交叉编译难点。

### 用户修正：优先下沉到 Node 层（Wails 可能更换）

用户指出这些都该在 Node 层实现且不影响性能，且 **Wails 这个宿主框架可能会换**。
核实后确认用户是对的，项目里已有先例：

- **`packages/shell-integration/src/core.ts`（551 行纯 TS）已经是 Node 层做 Windows 注册表集成**，
  形态为 `WindowsRegistryAdapter` 依赖注入 runner + `buildWindowsManagedShellPlan` /
  `applyWindowsShellPlan` / `inspectWindowsManagedShellPlan` + 所有权标记
  `xiranite.shell-integration/v1` + 冲突检测与回滚。
  `src/node.ts` 用 `registry-js` 与 `execFile("reg.exe", …, { windowsHide: true })` 落地。
- **`packages/nodes/neoview/src/platform/windows/`** —— 即 `platform/<domain>/` + `platform/windows/`
  的 Node 层分叉约定（`WindowsReaderExplorerContextMenuProvider`、`WindowsReaderShortcutResolver`、
  `WindowsSystemThumbnailProvider`、`ReaderExplorerExtensions`）。这是 macOS/Linux 的扩展点。
- `instanceId` 在 **Node 后端**生成（`packages/backend/src/index.ts:169`，`randomBytes(12).toString("hex")`），
  后端已是实例身份事实源；以 `server.listen(options.port ?? 0, …)` 取临时端口。
- `node_app_instance_windows.go` 用的是 **`windows.CreateMutex` + `winio.ListenPipe`**（不是 Job Object），
  管道名 `\\.\pipe\Xiranite.NodeApp.<sha256(nodeID|dataDirectory)[:12]>` —— 而 `net` 模块一套代码
  即可覆盖 Windows 命名管道与 POSIX `AF_UNIX`，**单实例与聚焦 IPC 可合并为一个 listener**，是简化而非复杂化。
- `local_backend.go` 已通过 stdout 管道与后端握手（`readBackendReady`），说明受控管道机制已存在。

**判据改为"是否必须先于窗口存在"**（不是按平台划分）：

| 归属 | 域 | 实现 | 热路径代价 |
|---|---|---|---|
| Node | 单实例互斥 | `net.createServer().listen(path)`，`EADDRINUSE` 即已有实例 | 启动一次 |
| Node | 实例复用 / 聚焦 IPC | 同一个 listener 接受连接 | 无 |
| Node | 后端不孤儿 | death-pipe `process.stdin.on("end")` → 退出 | 事件驱动 |
| Node | 子进程树回收 | POSIX `detached:true` + `kill(-pid)`；Windows `taskkill /T /F` | spawn 参数 |
| Node | 协议注册 | 声明式 plan + 三平台 materializer | 安装期 |
| Node | 隐藏子进程 | `windowsHide: true`（已有） | 无 |
| **宿主** | 任务栏身份 AUMID | 必须在进程创建首个窗口前设置 | — |
| **宿主** | 任务栏图标 | 需要窗口句柄 | — |
| **宿主** | 窗口几何 / 原生对话框 | 依附于窗口 | — |

- 路径派生是唯一平台差异：Windows `\\.\pipe\Xiranite.NodeApp.<key>`，
  POSIX `$XDG_RUNTIME_DIR/xiranite-nodeapp-<key>.sock` 回退 `/tmp`。POSIX 需处理崩溃残留 socket：
  `EADDRINUSE` 后尝试连接，`ECONNREFUSED` 即判为陈旧文件并 `unlink` 重试。
- death-pipe 必须用环境标记显式开启（如 `XIRANITE_PARENT_WATCH=1`），否则被不持有 stdin 的调用方
  启动时会立即退出。与现有 `XIRANITE_NODE_APP_SNAPSHOT_ID` / `XIRANITE_NODE_SOURCE` 做法一致。
- 协议注册 **macOS 运行时根本做不到**（`CFBundleURLTypes` 只能打包期声明），
  必须报 `unsupported`；Node 层产出 plist 片段供打包消费。
- 代码落点：生命周期类进 `packages/backend/src/platform/`（`instance.ts` / `parent-watch.ts` /
  `child-reaper.ts` / `capabilities.ts`），shell 关联类留在 `packages/shell-integration`。
  **注意 `packages/backend/src/index.ts` 已 933 行**（>800 预警、逼近 1000 上限），
  新逻辑不得继续堆进入口，须独立模块 + 入口组装。
- Go 侧只保留宿主 shim（AUMID / 窗口图标 / 窗口几何 / 原生对话框），
  `//go:build unix` 提取 mac+linux 共性，**删除全部 `_other.go`**（未覆盖平台应编译失败而非静默降级）。
  `service.go:698` 的 `events.Windows.WindowEndResize` 需换跨平台 resize 事件，
  否则组件窗口几何回写在非 Windows 上静默失效。

**待验证（不得当作已验证）**：bun 对 `net` 监听 `\\.\pipe\` 的支持与 `EADDRINUSE` 语义；
death-pipe 在宿主被 `SIGKILL`/`TerminateProcess` 时的触发时延；`detached: true` 在 Windows 上
对子进程树回收的实际效果（可能仍需保留 Job Object 作为 Windows 专属路径，则该域不满足"一套代码三平台"）；
`WindowsSystemThumbnailProvider.ts` 当前运行位置，确认下沉不给缩略图路径增加 RPC 跳数。

**产出**：`docs/adr/0063-keep-cross-platform-os-integration-in-the-node-backend.md`（status: proposed）。

**踩坑**：`find` 在 Git Bash 里仍被 Windows 版顶掉（`FIND: 参数格式不正确` / exit 2），
遍历目录一律用 Python；另外 `Glob` 在 `packages/` 下会因 `node_modules` 规模超时（30s），改用 `ls -R` 定向列目录。

### 范围已定（用户答复）

## 把 ClipM 屏蔽改动抽成独立提交放到 master（该改动原先混在 neoxide 的一个提交里）

**背景**：本次 ClipM 屏蔽的改动先被混进了 neoxide 分支的提交 `8f8bcffd`
（feat(neoview): implement CanvasReader with WebGPU support…，60 files / +3593/−70）。
用户要求把它**单独抽成一个提交放到 master**，两边都保留即可、不重写 neoxide 历史。

**做法（不需要 interactive rebase / cherry-pick 拆 hunk）**：
1. 先确认源分支该组改动只由这些文件承载：
   `git diff --stat master neoxide -- <我的 17 个路径>` → 得到 `16 files, 134 insertions(+), 54 deletions(-)`，
   与本地未提交时的 `git diff --stat` + 新增文件行数（95 + 39 = 134）**逐项吻合** ⇒ 这些路径上
   `master..neoxide` 的差异**就是**我这个改动，没有夹带别人的修改。
2. `git diff master neoxide -G "FOLDER_CLIPM_ENABLED|visibleFolderSortFields" --name-only` 复核无遗漏
   （只有 `.workbuddy/memory/2026-09-15.md` 属于记忆文件，不入提交）。
3. `git checkout neoxide -- <16 个显式文件路径>`（**逐文件列出，不要用目录**）把改动落到 master 工作区。
4. 校验 `git diff --cached <path>==neoxide`：`git diff --cached neoxide -- <paths>` 为空 ⇒ 内容 byte-identical。
5. `bun run commit '<中文 message>' <16 个路径>` → 得 `0bf80f62`（16 files, +134/−54），master 领先 origin 31。

**踩坑（本次卡了一轮）**：`scripts/commit-scope.sh` 的门禁 `git diff --check HEAD -- <paths>` 直接 exit 2，
输出 683KB 的 "trailing whitespace"，**每一行新增内容都被报**。
根因：本仓库 `core.autocrlf=true`，`git checkout <branch> -- <paths>` 写出的工作区文件是 **CRLF**，
而 `--check` 把行尾 `\r` 当空白；索引 blob 本身是 LF（`git diff --cached --check` 是干净的）。
解法：按**索引 blob** 重写工作区字节为 LF
（`execFileSync("git",["show",":"+p])` → `writeFileSync(p,buf)`），再 `git add` 刷新索引，
门禁立刻通过，且提交内容与 neoxide 的 blob 完全一致。
（另外 `git status` 在 LF 重写后会短暂显示 `MM`，但 `git diff` 为空——以 `git diff` 为准。）

**验证**：`git show --stat HEAD` = 16 files；`git diff HEAD neoxide -- <paths>` 为空（内容一致）；
提交后 `bunx tsc --noEmit` exit 0；工作区仅剩 ` m vendor/Xiranite-Nexus` 与两个无关未跟踪项。
**未推送**（master 领先 origin 31，用户未要求 push）。

**附带处理**：master 不跟踪 `.workbuddy/memory/2026-09-15.md`（neoxide 跟踪），
切回 master 时该文件被 git 删除。已用 `git show neoxide:<path>` 恢复到工作区（保持未跟踪、不入提交），
否则今天的记忆日志会只剩在 neoxide 分支里。

**下次这样做**：抽提交前先跑 `git diff --stat <base> <src-branch> -- <paths>` 与预期行数对账，
一次就能证明「没夹带别人的改动」；然后在 `git checkout <branch> -- <paths>` 之后立刻
按索引 blob 把工作区重写为 LF，再进 `bun run commit`，避免再撞一次 CRLF 门禁。
