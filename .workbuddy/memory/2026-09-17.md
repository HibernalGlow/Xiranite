## 解决 `git pull` 被本地改动阻塞

- **根因**：本仓库现在把 `.workbuddy/memory/*`（`MEMORY.md`、`2026-09-15.md`、`2026-09-16.md`）提交进了 git。
  本地未跟踪的同名记忆文件会在 fast-forward 时被上游"覆盖"而阻塞 pull；同时本地 7 个文件改动与上游 3 个提交（NeoView 预取修复）重叠，pull 直接 abort。
- **处理套路（已验证可行）**：
  1. 先把本地记忆文件 `mv` 到 `/tmp` 备份（`cp` 可能因并行竞争报 No such file，以 `mv` 的 `.local` 副本为准）。
  2. `git restore -- <冲突文件>` 丢弃本地重叠改动（用户明确确认这些重写是废弃的）。
  3. 再 `git pull --tags origin master` → 干净 fast-forward。
- **经验**：上游本次把预取逻辑重构成 `readerPreloadPolicy.ts` + `useReaderFrameStability.ts`，比本地被丢弃的那版更干净。
  以后 pull 前先检查 `.workbuddy/memory/` 是否被上游改动，避免再次被未跟踪文件阻塞。本地记忆目录现属"仓库共享"状态，不是纯本地。

## 事故与修复记录（重要）

1. **config-history 把整仓库提交了**：14:15 跑 backend 测试时出现 `6458371d3 config(xlchemy): update settings`
   （1881 文件、60 万行），作者 `Xiranite Config History`。
   - 根因：`packages/services/src/configVersionStore.ts` 的 `initializeRepository()` 用 `checkIsRepo()` 判断，
     而测试数据目录 `artifacts/test-runs/**` 位于本仓库内部 → 判定为"已是仓库"、跳过 `git init`，
     接着 `git commit --all` 作用到外层 Xiranite 仓库。历史上 7 月起已有 19 次同类提交（多为 1~29 文件）。
   - 处理：`git reset --mixed origin/master` 撤销；工作区 1853 个文件是**纯 CRLF 噪声**（`--ignore-cr-at-eol` 后真实差异只有本次 28 个文件），
     用脚本按索引 blob 还原为 LF；随后用 `bun run commit` 重新做成分域提交。
   - 修复：`isOwnedRepositoryRoot()` 用 `rev-parse --show-toplevel` + realpath 判定"必须是仓库根"，
     不够格就 `git init` 私有仓库；并把 `commit --all` 收紧为 `add 快照 + 提交`（无暂存改动时返回 null）。
     回归用例「keeps its history repository separate from a containing repository」已验证：旧实现下失败、修复后通过。
2. **修复必须 rebuild dist 才生效**：backend/宿主通过 `@xiranite/<pkg>/dist` 消费共享包，
   而本机 `packages/*/dist` 是 7 月的陈旧产物 → 修完 `src` 后第一次重跑测试仍被误提交。
   `cd packages/services && bunx tsc -p tsconfig.json` 重建后再跑，仓库不再新增提交。
   **教训：改共享包后要重建对应 dist（或整体 `bun run build:packages`），否则测试/宿主跑的是旧代码。**
