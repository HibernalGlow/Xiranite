## 解决 `git pull` 被本地改动阻塞

- **根因**：本仓库现在把 `.workbuddy/memory/*`（`MEMORY.md`、`2026-09-15.md`、`2026-09-16.md`）提交进了 git。
  本地未跟踪的同名记忆文件会在 fast-forward 时被上游"覆盖"而阻塞 pull；同时本地 7 个文件改动与上游 3 个提交（NeoView 预取修复）重叠，pull 直接 abort。
- **处理套路（已验证可行）**：
  1. 先把本地记忆文件 `mv` 到 `/tmp` 备份（`cp` 可能因并行竞争报 No such file，以 `mv` 的 `.local` 副本为准）。
  2. `git restore -- <冲突文件>` 丢弃本地重叠改动（用户明确确认这些重写是废弃的）。
  3. 再 `git pull --tags origin master` → 干净 fast-forward。
- **经验**：上游本次把预取逻辑重构成 `readerPreloadPolicy.ts` + `useReaderFrameStability.ts`，比本地被丢弃的那版更干净。
  以后 pull 前先检查 `.workbuddy/memory/` 是否被上游改动，避免再次被未跟踪文件阻塞。本地记忆目录现属"仓库共享"状态，不是纯本地。

## 修复 2 前置调查：macOS 回收站（比预期深，重新定级）

用真机探针（`/tmp/probe-trash-macos.mjs`，用已构建绑定调用 `getTrashCapabilities()` / `trashPath()`）实测：

- `getTrashCapabilities()` 在 macOS 返回 **`{deleteToTrash: true, list: false, restore: false}`**
  —— 所以之前那条"绑定在 mac 上支持 trash.list/restore"的判断是**错的**（smoke 输出里的
  `operation.trash.*` 是 API 面清单，不是运行时能力探测），已纠正。
- **trash 删除本身在 macOS 就是坏的**：`trashPath()` 抛
  `The AppleScript exited with error ... "Finder"遇到一个错误：发生权限违例。(-10004)`。
  根因：`trash-rs` 的 macOS 默认 `DeleteMethod::Finder` 走 `osascript` 驱动 Finder，
  需要「自动化」权限；而 **`DeleteMethod::NsFileManager` 不需要额外权限**（上游文档里的对比表写得很明确）。
  好消息：我们 pin 的 **`trash = "=5.2.6"` 已经带 `DeleteMethod`/`TrashContextExtMacos`**，
  所以不必升版本、不动 Windows 路径，只需改用 `TrashContext::new()` + `set_delete_method(NsFileManager)`。
- **上游永远不会给 macOS 的 list/restore**：`trash::os_limited` 的 cfg 明确排除 macOS，
  `src/macos/mod.rs` 只有 delete/purge；issue 里维护者说公开 API 不存在，put-back 信息在
  `.DS_Store` 里（私有格式、有竞态）。而 NsFileManager 与 Finder 的对比表里
  "Undo via Put back" 对 NsFileManager 是 ✗ —— 所以**不能依赖 Finder 的 put-back 元数据**，
  必须由 Xiranite 自己在删除时记录回收站落点与原始父目录，再据此还原。
- 落点获取有两条路：`objc2-foundation`（`trashItemAtURL_resultingItemURL_error` 传 `Some(&mut url)`
  能拿到精确落点；**0.3.2 已在 Cargo.lock 里**，因为 trash 的 macOS 分支依赖它）比
  "枚举回收站目录前后差分"（要自己算卷挂载点与 uid、处理重名去重）更精确也更短。
- 结论：cleanf 在 macOS 上要先修 delete（换 NsFileManager），再补"自建凭证 + 还原"，
  需要改 `native/czkawka-node/`、重建 darwin 绑定（release 构建 ~25 分钟）再跑 backend 集成测试。
  注意 `trash_api.rs` 里 `trash_error` 在 macOS 只被 unsupported 分支使用，换掉后要处理 unused 告警。

## 关于 `.node` 的跨平台问题（用户提问）

- 必须按 **OS × CPU 架构**（以及 Linux libc、Windows 工具链）分别构建，但**不需要**按 Node 版本构建
  （Node-API ABI 跨 Node 版本稳定，这是 napi-rs 相对 nan 的核心优势）。
- 本仓库已把矩阵编进寻址：`packages/czkawka-native/src/native-asset.ts` 用
  `xiranite-czkawka.${process.platform}-${process.arch}.node`；
  `@xiranite/native-loader` 的 `resolveNativeBindingPath` 顺序为
  环境变量覆盖 → `native/artifacts/<platform>-<arch>/` → 内嵌资产包（manifest + sha256）。
- 发布形态可选 napi-rs 惯例的 `optionalDependencies` 分平台子包，或复用本仓已有的内嵌资产包方案。
