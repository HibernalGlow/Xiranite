# 节点独立应用打包方案

> 状态：已确认，正在实现。本文是节点独立应用的交付契约与验收依据。

## 1. 问题

Xiranite 主项目持续开发时，构建、前端或某个无关节点的故障可能阻止整个桌面应用启动。NeoView、XLchemy、Czkawka 等重要且常用的重型节点因此失去可用入口。

目标是把选定节点在某个源码快照上冻结为可直接启动的 Windows 应用。源码快照可以包含目标依赖闭包内的未提交修改。冻结应用不依赖仓库源码、Vite 开发服务或主 Xiranite 进程，但继续实时使用 Xiranite 的正式配置和业务数据。

## 2. 已核实的基础

- 节点已经拆为 `packages/nodes/<id>` workspace 包，NeoView、XLchemy、Czkawka 均有独立 core、platform 和 CLI 导出。
- GUI 通过生成的 `packageModuleLoaders` 动态挂载节点，后端通过生成的 `generatedNodeSpecs` 懒加载节点 core/platform。
- `scripts/generate-node-registries.ts` 已支持 `XIRANITE_BUILD_ONLY_NODES`；`scripts/build-wails-local.ts --only-nodes <id>` 已能临时生成裁剪注册表、构建 Wails 应用，并在结束后恢复受影响的生成文件。
- 当前裁剪产物仍是完整 Xiranite 工作区外壳，不是直接进入单节点的产品形态。
- Wails 产物会嵌入前端、Bun 后端 bundle 和原生资产，但当前后端 bundle 仍需要机器上可解析到 Bun runtime。
- 默认配置位于 `%LOCALAPPDATA%/Xiranite/xiranite.config.toml`，项目数据库位于同目录的 `xiranite.db`。NeoView Reader 业务数据仍位于 `%APPDATA%/NeoView/thumbnails.db`，不属于 `xiranite.db`。
- TOML 写入已有跨进程文件锁；共享 SQLite 数据仍需要明确多进程写入和 schema 兼容契约。

## 3. 推荐基线

新增“节点应用快照”：由某个 Xiranite 源码快照构建出的、只承载一个节点的不可变运行时代码与资源集合。

推荐形态：

1. 复用 Windows/Wails 宿主和现有 host adapter，不另造第二套桌面框架。
2. 构建时只纳入目标节点及其真实传递依赖；前端直接挂载该节点，后端只注册该节点需要的路由和 runtime。
3. 冻结代码、前端资源、后端 bundle、Node-API 模块和版本清单；运行时不读取仓库 `src`/`dist`。
4. 节点应用拥有独立的应用身份、日志和进程生命周期；主窗口直接复用现有节点独立窗口 surface，不加载工作区壳层。
5. 节点业务配置和数据库沿用正式路径，并带 schema 握手、写入所有权和最小跨进程并发策略。
6. 按 XLchemy、Czkawka、NeoView 的顺序纵向交付，先稳定通用路径，再接入最复杂的 Reader 专属能力。

## 4. 预期使用路径

- 在 Xiranite 主应用未运行时执行 `bun scripts/package-node-app.ts <nodeId>`。
- 脚本冻结当前工作树中的目标依赖闭包，在隔离 staging 中执行构建与门禁。
- 构建完成后得到带节点名称和图标的应用；双击后直接进入该节点，不显示工作区和其他模块。
- “关于/诊断”页面显示节点快照版本、来源提交、数据路径、runtime 版本和兼容状态。
- 新版本由用户显式重新构建为新的内容寻址快照；独立应用不跟随开发工作区自动热更新。

## 5. 质询状态

所有关键分支已经逐项关闭，只剩对本文完整方案的最终共识确认。

## 6. 已确认决策

### D1：复用节点独立窗口 surface

节点独立应用启动后直接呈现当前 `FloatingComponentWindow` 所承载的节点界面、响应式布局和窗口控件。它不显示工作区、模块注册器或其他节点，也不另做一套节点 UI。

这项决定只冻结交互形态；实例身份和持久化按 D2、D16、D22 使用节点应用专属状态，不复用工作区 `componentId`。

### D2：从源码构建，首次启动创建专属实例

打包输入是当前 checkout 中目标节点的源码、GUI entry、共享 runtime 和真实传递依赖，不是运行中的工作区节点实例。打包过程不读取或复制任何 `componentId` 级 UI 状态。

节点应用首次启动时根据节点源码声明的默认状态创建自己的稳定实例身份，随后独立保存组件数据和窗口状态；工作区节点实例是否存在、被修改或被删除都不得影响节点应用。

### D3：实时共享正式配置和业务数据

节点应用不复制 `xiranite.config.toml`、`xiranite.db` 或节点自己的正式业务数据库。它与主 Xiranite 使用相同规范路径和实时数据；专属实例只隔离 `componentId` 级 UI 状态、窗口状态、日志和诊断数据。

### D4：允许主应用与节点应用并行运行

主 Xiranite、一个或多个不同节点应用必须可以同时运行并访问共享配置和业务数据。实现不得通过要求用户关闭其他 Xiranite 进程来规避并发；TOML 写入、SQLite 事务、迁移和重型后台任务都需要明确的跨进程协调。

### D5：兼容优先，允许通过重打包解决破坏性变化

配置和数据库 schema 的正常演进保持向后兼容，但不把任意旧节点应用永久兼容未来数据格式作为硬承诺。每个节点应用记录自身支持的数据契约范围；无法保持兼容时，重新打包是正式恢复路径。旧应用检测到超出契约范围后不得继续迁移或写入共享数据，并按 D6 进入诊断页。

### D6：不兼容时挂载诊断页

数据契约检查失败时，应用窗口仍可启动，但不得挂载节点、执行迁移或写入共享数据。窗口只显示快照版本、当前数据契约版本、数据路径和重新打包指引；重新打包后恢复正常运行。

### D7：复用现有 Bun，只构建节点后端切片

节点应用不内置 Bun，也不使用 `bun build --compile` 生成完整后端可执行文件。Wails 宿主启动机器上现有的 Bun，并携带只包含目标节点所需公共服务、节点 runtime、节点路由和真实传递依赖的后端 JS 切片；不得把完整 Xiranite backend API 打入每个节点应用。

Bun 解析沿用显式 `XIRANITE_BUN_BIN` 优先、随后系统 PATH/Scoop shim 的机制。节点后端切片必须与主后端复用公共服务和协议模块，不能复制实现形成第二套后端。

### D8：Bun 最低版本门禁与启动能力握手

快照清单记录构建时 Bun 版本和最低支持版本。运行时 Bun 低于最低版本或无法找到时进入诊断页；高于已测试版本时先执行节点后端能力握手，握手通过即可运行并记录兼容性警告，不要求与构建版本完全一致。

### D9：默认产出单个便携 exe

每个节点应用默认产出一个带节点名称、版本信息和图标的 Windows exe，不要求安装，也不附带完整 Xiranite 或 sidecar 目录。前端、节点后端 JS、快照清单和目标节点真实需要的原生资产嵌入 exe，运行时按内容哈希释放到缓存目录。Scoop 清单和快捷方式属于后续可选发布层。

### D10：通用 opt-in 契约，三个重型节点首期验收

打包器不硬编码具体节点。可打包节点按 D23 使用最小 opt-in，已有事实源负责应用元数据、窗口偏好、导出和依赖；缺少声明或资格门禁失败时脚本明确报错。首期以 NeoView、XLchemy、Czkawka 完成端到端构建与运行验收，其他节点随后按同一契约接入。

### D11：脚本负责源码打包，产物只提供 GUI

节点应用通过仓库内的 Bun 脚本从源码构建，不开发独立构建器 GUI 或 companion exe。脚本在 Xiranite 主应用和业务后端均未运行时直接扫描当前 checkout 的节点定义与资格声明。

打包核心实现为可测试、可复用的 TypeScript 模块，由薄脚本入口调用。脚本是开发/构建工具，不是节点自身的 CLI 产品接口。

节点应用直接依赖节点包的 `core` 和 `platform` 导出。节点包中的 `cli` 只是另一种入口适配器，打包流程和节点应用运行时不得通过 CLI 入口间接调用核心。

脚本选择源码节点定义，不绑定当前窗口或工作区组件；节点 surface 的“在独立窗口打开”只作为产物运行后的界面基线，不是打包来源。主应用内的 `ModuleRegistry` 不承担源码打包入口。

产出的节点应用只提供 GUI。它直接复用节点包的 `core` 和 `platform`；节点包中的 `cli` 不进入用户界面，也不作为应用运行入口。

### D12：冻结目标依赖闭包的当前工作树内容

源码存在未提交修改时，打包包含目标节点及其真实传递依赖在当前工作树中的实际内容，不强制用户先提交。构建器先把依赖闭包复制到隔离 staging 目录，再生成注册表和构建产物，不得改写工作区生成文件或源码。

快照清单记录 Git commit、dirty 状态、纳入文件的内容哈希、构建时间及工具版本。未进入目标依赖闭包的其他节点和无关工作树修改不得进入产物。

### D13：核心脚本一次构建一个节点

打包脚本每次必须接收且只接收一个节点 ID，例如 `bun scripts/package-node-app.ts neoview`。单次事务只构建、验证和输出该节点的产物；未来批处理能力也必须串行调用单节点事务，不能并发执行重型节点构建。

### D14：同一节点应用快照单实例

同一快照只允许一个应用进程和一套节点后端运行。重复启动时通过 Windows 命名互斥量和本地 IPC 通知已有进程恢复并聚焦主窗口，不创建第二个 Bun 后端。不同节点的独立应用仍可并行运行。

### D15：同一节点的不同快照互斥，不新增协调表

节点应用之间按节点 ID 和数据根目录互斥；同一节点的旧、新快照不能同时运行。新版检测到旧版后聚焦现有应用并显示其版本，用户关闭旧版后再启动新版。

互斥和唤醒完全使用 Windows 命名互斥量及本地 IPC，不在 `xiranite.db` 中增加进程租约、活跃版本或协调状态表，以保持最小数据库维护量。主 Xiranite 与节点应用仍可按 D4 并行运行。

### D16：宿主自动持久化节点应用状态

节点正式配置继续使用 `xiranite.config.toml`，业务数据继续使用既有数据库；只有独立应用的组件数据、窗口尺寸和临时 UI 状态写入 `%LOCALAPPDATA%/Xiranite/node-apps/<nodeId>/` 下的状态文件。

状态能力由共享节点应用宿主统一实现，节点继续使用现有 `host.state.getData/patchData`，不得为独立应用增加节点专属持久化代码。宿主复用现有 `proper-lockfile` 和 `write-file-atomic` 完成锁定、合并、原子替换与损坏恢复，并使用节点声明的现有 schema 校验状态。

每个节点应用使用独立 WebView2 profile，使 `localStorage`、`sessionStorage` 和浏览器缓存自动隔离；这同样由宿主配置完成，不要求节点感知运行形态。

### D17：使用内容寻址的不可变产物

重新打包不覆盖旧 exe。构建器根据规范化的源码依赖闭包、节点打包声明、目标平台和影响产物的工具链版本计算快照 ID，并输出例如 `build/node-apps/neoview/NeoView-<snapshotId>.exe` 的不可变文件。

快照 ID 不包含构建时间，也不依赖最终 PE 文件自身，避免循环计算并保证相同输入得到相同身份。完整 ID 和输入清单嵌入 exe；文件名使用足够长的短哈希。同一输入已有验证通过的产物时可以直接复用，不重复构建。旧快照天然保留并可直接用于回滚，但 D15 仍禁止同一节点的不同快照同时运行。

### D18：最终快照不自动清理

已验证并发布到 `build/node-apps/<nodeId>/` 的哈希 exe 永不按数量、时间或磁盘压力自动删除，只能由用户明确清理。staging 目录、可重建编译缓存和失败中间产物可以按安全策略回收；清理它们不得影响任一已发布快照的运行。

### D19：不可跳过的节点级发布门禁

打包只运行目标节点及共享宿主所需的定向门禁，不运行全仓或无关节点测试。门禁至少覆盖节点包 build/test、目标前端 typecheck 与裁剪 Vite 构建、节点后端切片及协议握手、原生资产哈希与真实加载，以及最终 exe 使用隔离临时数据目录完成窗口、后端和节点挂载 smoke。

所有重任务严格串行，Vitest 使用单 worker。任一步失败都不得发布哈希 exe，也不提供绕过门禁后发布的 `--force`；旧快照保持不动，失败尝试只保留诊断日志和可安全清理的中间产物。

### D20：宿主统一管理关窗与后台任务

没有活动任务时，关闭节点应用窗口直接退出应用和 Bun 后端。有活动任务时，宿主提供继续后台运行、取消任务并退出、返回窗口三种明确操作；继续后台运行时隐藏窗口并显示节点应用托盘。

托盘的恢复窗口、任务状态和退出能力由共享宿主根据现有 operation 状态生成，不要求节点声明或实现。显式退出时宿主先请求取消活动任务并等待清理完成，再终止后端进程。

### D21：自动恢复后端，不自动重放任务

Bun 后端意外退出后，Wails 宿主自动重新启动节点后端并重新执行能力握手，短时间内最多尝试两次；连续失败后进入诊断页。前端和节点应用状态保持挂载，握手成功后重新连接。

崩溃时的活动任务标记为意外中断，绝不自动重放删除、移动、转码或其他有副作用的操作。诊断页显示退出码和崩溃日志，并允许用户重新启动后端；是否重新执行任务由用户检查结果后决定。

### D22：跨快照自动验证并继承 UI 状态

每个快照维护独立的节点应用状态文件。新快照首次启动时由宿主读取最近快照状态，并使用节点现有 `schemas.data` 自动验证；通过后复制为新快照自己的初始状态，失败则使用节点默认状态启动。

验证失败不得覆盖、删除或迁移旧状态，旧 exe 回滚时仍恢复原现场。正式配置和业务数据库不参与这次复制，继续按 D3 实时共享；节点不提供独立应用状态 migration。

### D23：最小 opt-in，默认推导打包声明

普通节点只需在现有应用节点定义中声明 `nodeApp: true`。构建器从同一事实源推导名称、版本、图标、窗口偏好、`core/platform` 导出、依赖闭包和原生资产，不要求复制元数据。

只有无法通用推导的能力使用 `nodeApp` 对象覆盖，例如 NeoView 专属后端 feature 或节点级 smoke 就绪条件。推导缺失或冲突时资格门禁明确失败，不用静默默认值构建不完整应用。

### D24：首期只保证当前 Windows 开发机本地使用

首期产物面向当前 Windows 架构、本机现有 Bun 以及本机规范配置和数据库路径，不包含代码签名、安装器、自动更新或跨机器数据迁移。exe 可以被复制，但其他机器运行属于未保证场景；跨机器 prerequisite 与 portable 数据策略不进入首期门禁。

### D25：每个节点应用始终运行自己的后端切片

节点应用无论主 Xiranite 是否正在运行，都使用现有 Bun 启动快照内嵌的节点后端 JS 切片，不探测、不连接也不复用主应用后端。节点应用只与主项目共享正式配置和数据库，不共享后端进程、端口或代码版本。

### D26：日志物理隔离但沿用同一日志体系

节点应用继续使用 `@xiranite/logging` 的事件 schema、JSONL writer、gzip 轮转、查询和诊断能力，但不写入主项目 `%LOCALAPPDATA%/Xiranite/logs`。每个节点应用把日志写入与原子状态相同的数据根，例如 `%LOCALAPPDATA%/Xiranite/node-apps/<nodeId>/logs/<snapshotId>/`。

日志 source 同时包含节点 ID 和快照 ID，构建日志与运行日志可区分。日志沿用现有大小/文件数轮转策略，可自动回收；D18 的最终 exe 永不自动删除规则不适用于日志。

### D27：共享数据库采用无新增表的最小并发方案

`xiranite.db` 的 schema 初始化和 migration 使用跨进程文件锁串行执行；所有本地 libSQL 连接统一设置有限 `busy_timeout`，正常读写继续依赖短事务和 SQLite/libSQL 自身的写入序列化。节点应用不新增租约表、writer 服务或其他协调 schema，也不因本功能改变 journal mode。

锁等待超时返回明确、可重试的 busy 错误，不无限等待。NeoView `thumbnails.db` 保持原 journal、表、索引、metadata 和兼容策略，只使用其现有事务及等待机制。

### D28：节点后端使用固定最小基线加显式 feature

所有节点应用后端固定包含健康/版本握手、日志、节点配置、运行/取消/进度、运行历史、本地文件及通用文件操作。节点专属路由通过 `nodeApp.backendFeatures` 显式加入，例如 NeoView Reader 后端。

工作区 CRUD、模块注册器、其他节点 runtime、主应用设置和 Nexus IPC 不进入节点后端。import graph 只裁剪实现代码与传递依赖，不能决定业务能力，避免动态加载路径被静默移除。

### D29：按 XLchemy、Czkawka、NeoView 顺序实施

XLchemy 首先验证通用 GUI 壳、slimg 原生资产、共享配置、长任务和托盘生命周期；Czkawka 随后验证 czkawka native、文件操作、取消、历史和数据库并发；NeoView 最后接入 Reader 专属后端、NeoView 数据库、复杂窗口状态和更多运行资产。

顺序只控制实施风险，不能把前一节点完成视为整项功能完成，也不能为后续节点复制打包器或宿主实现。

### D30：三个首期节点全部通过真实代表流程才算完成

XLchemy 必须使用临时图片完成真实转码、进度、取消和结果输出；Czkawka 必须扫描临时目录得到真实结果并验证文件操作、历史及取消；NeoView 必须打开临时书籍并真实渲染页面，验证 Reader 后端、配置和兼容数据库写入。

三者都必须在主 Xiranite 未运行时启动，并使用隔离数据根验证主应用与节点应用并发，不访问默认真实数据库。UI 使用 Vitest Browser Mode；进程、窗口和后端生命周期使用 Wails/Go 集成测试。非 Windows 构建、全仓测试和无关节点不属于首期完成门禁。

## 7. 架构边界

### 7.1 声明与发现

- 现有 `AppNodeEntry`/节点定义增加最小 `nodeApp` opt-in。
- 生成器继续作为节点、GUI 和 runtime 事实源；节点应用模式只生成一个目标节点。
- 名称、版本、图标、窗口偏好、包导出和原生依赖默认推导；特殊后端 feature 与 smoke ready 条件显式覆盖。

### 7.2 打包器

- 薄 Bun 脚本负责参数、进度、日志和退出码。
- 共享 TypeScript packager 负责依赖闭包、staging、快照 manifest、内容哈希、串行门禁和最终发布。
- packager 不改写 checkout，不启动主 Xiranite，也不访问默认真实数据库。

### 7.3 节点应用前端

- 专用 frontend entry 只挂载全局 provider、诊断边界和 `FloatingComponentWindow` 等价 surface。
- 不加载 WorkspaceLayout、模块注册器、其他节点 loader 或工作区恢复。
- 节点继续消费同一 `NodeHostApi`；独立应用 adapter 替换组件状态、窗口生命周期和诊断实现。

### 7.4 节点后端

- `createNodeAppBackend()` 组合 D28 的固定公共基线和目标节点 features。
- 后端 JS 由现有 Bun 执行并由 Wails 宿主监管，不连接主应用后端。
- 公共 route/service/repository 从现有包复用，不复制完整 backend 或节点核心。

### 7.5 Windows/Wails 宿主

- 同一宿主模板注入节点 manifest、品牌资源、前端、后端 JS 和目标原生资产。
- 宿主负责单实例互斥、IPC 聚焦、WebView2 profile、Bun 解析/握手、后端重启、托盘和进程回收。
- 平台专属代码留在 desktop adapter；共享 TS 契约不硬编码 Windows API。

## 8. 构建流程

1. 解析单个目标节点并验证 `nodeApp` 资格。
2. 计算目标源码和真实传递依赖闭包，复制当前工作树内容到隔离 staging。
3. 生成只含目标节点的 frontend/runtime registries 与节点后端 feature manifest。
4. 在 staging 中串行构建节点包、共享包、前端、后端 JS 和必要原生资产。
5. 生成规范化 snapshot manifest，并由输入内容计算 snapshot ID。
6. 构建带节点品牌资源的单个 Wails exe。
7. 使用隔离数据根执行 D19/D30 门禁。
8. 只有全部通过才把 exe 发布为 `<NodeName>-<snapshotId>.exe`；失败只写诊断日志。

## 9. 运行流程

1. 获取按节点 ID和数据根命名的互斥量；已有节点应用时通过 IPC 聚焦并退出新进程。
2. 解析 Bun，检查最低版本并释放内容寻址的后端/原生资产缓存。
3. 检查数据契约；不兼容时直接显示诊断页。
4. 启动节点后端切片并完成健康、版本和 capability 握手。
5. 自动加载或继承快照 UI 状态，挂载节点独立窗口 surface。
6. 运行期间共享正式配置和业务数据库，应用状态与日志写入独立节点应用目录。
7. 后端崩溃按 D21 恢复；关窗和后台任务按 D20 处理。

## 10. 数据目录

```text
%LOCALAPPDATA%/Xiranite/
├── xiranite.config.toml              # 与主项目实时共享
├── xiranite.db                       # 与主项目实时共享
└── node-apps/
    ├── data-contract.json            # 共享、单调递增的兼容契约标记
    └── <nodeId>/
        ├── state/<snapshotId>.json   # 宿主原子维护的 UI 状态
        ├── active-operations.json    # 崩溃后只记录中断、不重放的短暂 journal
        ├── logs/<snapshotId>/         # 同体系、独立目录的运行日志
        ├── webview2/                  # 节点应用 WebView2 profile
        └── runtime/<contentHash>/     # 释放的后端和原生资产缓存
```

NeoView 的 Reader 业务数据继续位于 `%APPDATA%/NeoView/thumbnails.db`，不迁入上述目录。

## 11. 首期非目标

- 不做应用内或独立 GUI 构建器。
- 不把节点 CLI 作为应用入口。
- 不内置 Bun，不编译完整 backend exe。
- 不支持一次构建多个节点或一个 exe 承载多个节点。
- 不做签名、安装器、自动更新、跨机器数据迁移或非 Windows 发布。
- 不新增节点应用数据库、进程协调表或 NeoView 业务表。
- 不保证任意旧快照永久兼容未来破坏性 schema。
